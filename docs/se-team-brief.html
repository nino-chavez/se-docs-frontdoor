SE Docs Front Door

One Slack question, one cited answer — drawn from every doc source we already use. This brief covers the problem, what three research tracks found, the decision analysis, and the full scoping interview that locked the design.

The decision

Configure first. Build only on evidence. Buy nothing.

Anthropic already ships Claude Tag, the successor to Claude in Slack. Our organization already has Enterprise seats, the Atlassian connector is live, and every SE has access. The next step is a two-week pilot in one SE channel: zero code, admin toggles only. A thin custom bot is fully specified as the fallback and activates only if the pilot fails a named test. We can retire the buy shelf (Glean, Onyx, Dust, and Slack's Agentforce) because our access model and existing Claude spend remove its two justifications.

Configure — pilot now Build — contingent Buy — retired

01 · Problem

Research time goes to finding, not reasoning

SEs assemble client solutions from documents scattered across Jira and Confluence, Google Drive, Slack threads, NotebookLM notebooks, one-off local files, and internal and public doc sites. None of these search each other. The working fallback is the shoulder-tap: ping one of the two or three senior SEs who hold the tribal knowledge.

That fallback is the measurable cost. It taxes the seniors, it caps how fast newer SEs ramp, and it means answer quality depends on who happens to be online. The front door exists to replace the shoulder-tap with something faster that cites its sources — so the metric for success is senior-SE deflection: fewer “quick question” pings, measured against a baseline we capture before launch.

02 · Research

Three tracks, run in parallel, verified against primary sources

Track 1 · What Anthropic ships
  • Claude Tag is this product off the shelf: @Claude in channels, access to enabled connectors, per-channel scoped identities, spend limits, audit log. Legacy Claude-in-Slack force-migrates to Tag on Aug 3, 2026.
  • Our rails already exist: Claude Enterprise seats org-wide, Atlassian connector live — proven by an adjacent internal POC (the GEM enablement-triage bot) that creates Jira tickets from Slack today.
  • If we ever build: Slack bot → Claude Messages API → search tools that return search_result blocks, which makes verifiable citations automatic.
Track 2 · The market
  • Buy options ranked: Slack’s native Slackbot/Agentforce (Salesforce’s model, permission story undocumented), Glean (best surface, ~$60k/yr floor), Onyx and Dust (Claude-friendly, $0–$30/seat).
  • All four carry the same headwind: we already pay for Claude Enterprise. A second overlapping AI spend needs its own justification.
  • Adoption reality check: the median enterprise doc-bot falls under 15% weekly-active by month six. The #1 retention lever in the data is citation quality — answers people can verify.
Track 3 · Retrieval architecture
  • 2025–26 consensus: federated live search beats a copied index for permission-sensitive corpora — the agent queries each source’s own search at question time, so nothing is duplicated and nothing goes stale.
  • Permission-leaking indexes are now the #2 risk on OWASP’s LLM Top 10, with real incidents. Federation avoids the entire class.
  • Indexing earns a place only for sources with weak search. Our inventory has none of the usual suspects.
Verified the hard way #1 — NotebookLM is not a queryable source. Google publishes no API for asking a notebook questions (the Enterprise API manages notebooks; it cannot query them), and notebook sources are internal copies, invisible to Drive search unless they were imported from Drive. Norm, not code: originals live in Drive; notebooks import from Drive.
Verified the hard way #2 — Drive is unread, and the reason is configuration. Superseded 2026-07-28. This flag previously blamed an open Anthropic Shared Drive bug and prescribed a custom-bot fallback. Both were wrong: the bug is on a different connector surface, a caveat research/research-reference-grade.md had already graded warn and this brief kept asserting anyway.
What replaces it. Anthropic’s enterprise-search docs list Drive among supported sources, so the gap in Ask Commerce is an unfinished setup, not a platform limit — no custom build is warranted. Shared Drives specifically stay unconfirmed; the docs are silent, which is not the same as negative. Owner: research/prior-art/ask-commerce.md AC-1.

03 · Analysis

Why configure wins, and exactly when build takes over

The scoping interview (next section) settled the two facts that decide everything. First, access is uniform — every SE can already open every doc in scope — which removes the one hard requirement (per-user identity plumbing) that a custom build uniquely serves, and with it the entire case for buying a permission-syncing product. Second, every SE already has a Claude Enterprise seat, so Claude Tag reaches the whole team on day one at no incremental cost.

Everything else the interview locked — answer labels by source authority, surfacing conflicting docs instead of silently picking one, pinning public-doc answers to current-stable versions — is enforceable through channel instructions. Whether instruction-level enforcement is good enough is precisely what the pilot measures. The build branch stays fully specced and activates on any of four named triggers:

TriggerWhat it meansThe build fix
Drive unreadable after AI Ops connects itSetup completed and Shared Drives still return nothingCustom Drive search tool — but only then. Untriggered as of 2026-07-28: the setup has not been requested, so the fallback has nothing to fall back from
Label inadequacyPrompt-level authority tiers / conflict flags prove too lossyBot formats answers deterministically
Scoping gapsTag can’t restrict Slack search to named channels, or CMS sites matterCustom tools with explicit scopes; targeted crawl
Telemetry ceilingDeflection can’t be measured by survey + senior self-reportBot in the middle logs every question

Design commitments that bind both branches: read-only v1 as a hard line (this tool researches; it never writes to Jira, docs, or anything else), citations on every answer, async-first (no mid-call latency engineering in v1), and wide corpus with authority-tier labels rather than a curated allowlist.

05 · Next steps

What the pilot needs before go-live

Ask 1

A Claude Enterprise admin

Toggle the Drive and Slack connectors, bless one pilot SE channel, invite Claude. The rails were already cleared by the adjacent triage POC — this is minutes, not a project.

Ask 2

Two or three senior SEs

Baseline their current ping volume, then adopt one behavior: “ask the bot first, then come back to me.” They are both the measurement and the adoption engine.

Ask 3

Two weeks of real questions

The pilot tests four things: Shared-Drive visibility, label and conflict-flag quality, citation usefulness, and a corpus census. Any failure activates the specced build fallback — nothing is wasted.
